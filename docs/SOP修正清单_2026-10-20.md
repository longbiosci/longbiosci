### 1. 🔴 7762988 根本不是「每月 15 日」

**实测**（`automation_list` 原始返回值）：

| 字段 | 实际值 |
|---|---|
| name | 月度研究热点综述·每月15日 |
| description | 汇总当月衰老与长寿领域研究热点与趋势，产出月报入元层 |
| **schedule_desc** | **每月 \*/14 日 04:34** |
| **cron_expr** | **`0 34 4 */14 * 2`** |
| last_run_at | **2026-10-20 04:34** |
| next_run_at | 2026-10-27 04:34 |

**cron 的真实语义**：`*/14` 是「月内每 14 天」，配合 `* 2`（周二）过滤，2026 年落点是 **1/15/29、2/16/30、3/17/31…**——不是每月 15 日，而是「约每 14 天、且必须落在周二」。

**已造成的事故**：SOP 判「每月 15 日交付」，10-15 是周四，cron 不触发；真正的触发日是 **10-20 04:34**，产出了《月度研究热点综述_2026-10》`dXzxgtkeYPXT`。而 SOP 写的是「每月 15 日」，10-15 到 10-18 期间没有任何告警——**这一天多的产出是靠次日的增量巡检偶然捞到的**。

**修正**：

- 描述改为：`每 14 天（逢周二）04:30 · 约每月两次（1/15/29 或 2/16/30 落点）`
- SOP 的交货期望表改为：**按 `next_run_at` 判，不按日历日期判**；判空窗的参照系是上一次 `next_run_at` + 3 小时。

> ⚠️ 但这里有个更根本的问题要你定：**「月度综述跑成两周一次」显然不是设计意图**。是 cron 写错了（应 `0 34 4 15 * *`），还是就是想要两周一次、只是名字没改？我倾向前者——因为产出文件名是《月度研究热点综述_2026-10》按月编号，两周一次会出现「一个月两份都叫 2026-10」。**这个需要你决定，我不擅自改上游 cron。**

### 3. 🔴 「保留 3 条」与「不得删除」直接打架

同一个任务 7660605 的 description 里同时写着：

两条规则在这个任务上**不可能同时满足**：留痕要「保留 3 条滚动」，反馈段要「永久保留」。结果是 description 只增不减。7762989 现在同时挂着 10-16 交付记录、10-18 两条质检、10-17 PDF 归档——已经 5 段并存，早超了「保留 3 条」。

**修正**（需要你拍板选一个）：

- **方案 A**：留痕改用**独立文件**（网盘元层 `留痕_<任务ID>.md`），description 只留一行指针。好处：description 恢复干净，历史可查，不打架。代价：多一个文件。

我倾向 **A**。

### 7. 🟠 推送环节在 SOP 里根本不存在

SOP 的 §3 收尾于「管线全绿」，但**绿色 ≠ 上线**。今天这一轮的实际路径是：

```

        → 串行版 17 分钟卡死
        → 重写快通道 push_via_api2.py 才成功
```

**修正**：§3 增加一个**强制环节**「推送与线上核验」，且在 SOP 里固化成：

| 项 | 规定 |
|---|---|
| 通道 | 先试 `git push`（60 秒超时）；不通即走 `scripts/push_via_api2.py` |
| 禁止 | **任何情况下不得 force push**；`push_via_api2.py` 内已硬编码 `force: false` |
| 前置 | 基准断言：本地快照 tree 必须等于远端 tree，不等即中止 |

这条今天已经用 `scripts/push_via_api2.py` 落地了，SOP 需要把它写进去，否则下次换人接手还会去写一遍串行版。

## 四、连带发现（不在本次修正范围，需另行处理）

**`123195` 这个「运营日志字节数」被当成实测值写进了 `data/verified-sizes.json`，但它是错的。**

上午的巡检把该值登记为「10-18 实测 123,195 B」，而实际 10-20 的日志是 **155,541 B**（下载核验）。
影响：`build_manifest.py` 用这个过期实测值覆盖缓存，于是清单长期显示一个偏小 3 万字节的数字。
它**不会造成误判**（因为 >0 恒成立），但会让「字节数是否变化」这个信号失真。
已确认 `verified-sizes.json` 的机制没问题（实测覆盖缓存是对的），问题只是**实测值本身需要随每次下载刷新**。
建议：给它加 `stale_after_days`，超过 7 天的实测值降级为「线索」而非「事实」。

（我这次没有改 `verified-sizes.json`，因为它不在 SOP 文档范围内，且改动会影响清单生成结果——留给你决定。）
