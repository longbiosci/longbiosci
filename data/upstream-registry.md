## 三、已知陷阱（每条都是踩过的坑，务必遵守）

1. **`dir_list` 返回的 `size` 是陈旧缓存，绝对不可用于判空**。
   已 **4 次**实测撞上「列表 size=0、实际几十 KB 完整正文」：
   - `dNTCoBPwiOnt`（五刊 10-09）列表 0 → 实测 **89,241 B**
   - `dsMQHIJKCTLS`（交叉周报 10-12）列表 0 → 实测 **33,644 B**
   > **判空前无例外必须 `file_download` + `stat -c%s`**。

2. **`7762988` 的 cron 是 OR 语义**，别当成「每月 15 日」。
   `*/14` 与 `* 2`（周二）在满足其一时触发。下次 2026-10-20 是**周二**，走的是「周二」分支而非「14 日」。

3. **`12409847` / `12179175` 的描述与实际 cron 不一致**。以 `cron_expr` 为准，不要照描述排班或告警。

4. **`运营日志.md` / `运营待办清单.md` 有两个任务在并发写**。
   实测现象：我 07:5x 上传后（`dRlRAPWevRku` 96,773 B / `dVisoPwrcwVm` 42,341 B），几分钟后 mtime 又被推后、大小变为 64,212 B / 31,351 B —— 系另一任务在 10:30 轮次回写。
   > **回写运营文档前必须重新 `file_download` 最新版**，否则覆盖他人改动。

5. **推送侧有假 `origin/main` 陷阱**。
   `git fetch <带 token 的 URL> main` 只更新 `FETCH_HEAD`，**不更新 `origin/main` 远程跟踪分支** → 会误判「纯 fast-forward」而实际早已分叉。
   正确做法：临时 `git remote set-url origin <带 token URL>` 再 fetch，用完立即还原。

6. **🔴 git 的低速保护会自己掐断传输（2026-10-17 定位，连续害了两轮「推送阻塞」的误判）**。
   本机到 github.com 的实际带宽约 **< 500 B/s**，而 git 默认「60 秒内平均低于 1 KB/s 即中断」。
   于是 `fetch` / `unshallow` 每次都在 60–132 秒后自己停掉，报
   `Operation too slow. Less than 500 bytes/sec transferred`。
   **前两轮把它误判为「网络不通」和「本机无凭据」**——但 `git ls-remote` 一直秒回，网络其实是通的。

   解法（实测：unshallow 从 60 秒超时变 **2 秒完成**，push **2 秒完成**）：
   ```bash
   git -c http.lowSpeedLimit=0 -c http.lowSpeedTime=999999 <fetch|unshallow|push> ...
   ```
   所有 git 远程操作都应带上。另：凭据可从历史执行日志 `/root/.codebuddy/logs/` 中取到
   可用 PAT（用 `git ls-remote` 验证通过后使用），用完立即清理临时文件、还原 remote URL。

7. **`evidence/` 三个分级页是静态遗留，无任何脚本生成**（2026-10-17 发现）。
   `evidence/index.html` 写 A 94 / B 269 / C 17 篇，实际 articles.json 是 **A 132 / B 311 / C 103**；
   三个分页各只列 25 / 25 / 18 条。每次证据分级变动都会让它与事实源多一处不一致，
   → 需要新建生成器纳入管线（已列入运营待办）。

### 3.5 证据分级「回退」陷阱（2026-10-17 新增，当日复现 2 次）

**现象**：文章页 HTML 里更正了证据分级，但 `data/articles.json` 仍是旧值，
站内出现「同一篇文章两个分级」。

**根因**：`build-index.py` 的 `main()` 把已登记记录当**权威基线整体保留**
（注释原文：「1) 现有登记（权威基线）」），HTML 侧改动不回写 JSON。
而 articles.json 又是首页 / 话题页 / 搜索索引的数据源。

**触发场景**：只要远端带回一份**旧的 articles.json 快照**并合并进来，
本地已更正的分级就会被那个旧值覆盖 —— 2026-10-17 合并远端 2 个新稿提交时
PROMETHEUS 的 A 就是这样被回退成 C 的。

**解法**：`python3 scripts/sync-evidence.py . --write`
（幂等，只同步 evidence、**不碰 desc** —— 已知约 57 篇的 desc 只存在于 JSON 侧，
一并覆盖会静默丢数据）。建议在每次合并远端分支后例行跑一次。

### 7.4 本轮抓到并已修的两个静默缺陷（都会污染事实源）

| 缺陷 | 现象 | 已修 |
|---|---|---|
| `build_manifest.py` 的 `DEFAULT_RAW` 硬编码到**另一个会话**的 artifact 目录 | 不传参数时静默读一份**陈旧抓包** → 清单里凭空多出已删除的旧文件，本轮新产出又缺 name/ext/mtime | 默认改为仓库内 `data/nd_raw.json`，找不到就**明确报错**要求先跑 `nd_dirlist.py` |
| `verified-sizes.json` 里已不存在的 file_id 会被**补成合成行** | 文件被上游删除后，以 `name=file_id` / `ext` 空 / `modify_time=0` 的**幽灵行**长期赖在事实源里 | 不再合成，改为打印 ⚠️ 告警列出这些 id，由人决定是否从 `verified-sizes.json` 摘除 |

→ 教训：**方向正确的补丁（用实测值覆盖缓存）也会在边界上反向投毒**。
  已删除文件的正确归宿是**从清单里消失**，不是留一条残缺记录。
  与前面「检查全是哑弹」那条纪律同源：最大的敌人不是没检查，
  而是**读了不该读的旧东西还不报错**。
