## 三、已知陷阱（每条都是踩过的坑，务必遵守）

1. **`dir_list` 返回的 `size` 是陈旧缓存，绝对不可用于判空**。
   已 **4 次**实测撞上「列表 size=0、实际几十 KB 完整正文」：
   - `dNTCoBPwiOnt`（五刊 10-09）列表 0 → 实测 **89,241 B**
   - `dsMQHIJKCTLS`（交叉周报 10-12）列表 0 → 实测 **33,644 B**
   > **判空前无例外必须 `file_download` + `stat -c%s`**。

2. **`7762988` 的 cron 是 OR 语义**，别当成「每月 15 日」。
   `*/14` 与 `* 2`（周二）在满足其一时触发。下次 2026-10-20 是**周二**，走的是「周二」分支而非「14 日」。

3. **`12409847` / `12179175` 的描述与实际 cron 不一致**。以 `cron_expr` 为准，不要照描述排班或告警。

4. **`运营日志.md` / `运营待办清单.md` 有两个任务在并发写**。
   实测现象：我 07:5x 上传后（`dRlRAPWevRku` 96,773 B / `dVisoPwrcwVm` 42,341 B），几分钟后 mtime 又被推后、大小变为 64,212 B / 31,351 B —— 系另一任务在 10:30 轮次回写。
   > **回写运营文档前必须重新 `file_download` 最新版**，否则覆盖他人改动。

5. **推送侧有假 `origin/main` 陷阱**。
   `git fetch <带 token 的 URL> main` 只更新 `FETCH_HEAD`，**不更新 `origin/main` 远程跟踪分支** → 会误判「纯 fast-forward」而实际早已分叉。
   正确做法：临时 `git remote set-url origin <带 token URL>` 再 fetch，用完立即还原。
